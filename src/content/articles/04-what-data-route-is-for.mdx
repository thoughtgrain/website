<Dropcap text="Every page on this site contains one line that looks like configuration left in by mistake. It isn't. It's the entire mechanism by which a static file knows what it's supposed to be." />

Here it is, from `/about/`:

```html
<div id="root" data-route="/about/" data-base="../"></div>
```

Two attributes. Let me take them one at a time.

## The line

That div is empty when the build writes it. By the time you load the page it is full of markup, because a later phase renders the page and injects it. But the div itself, and the attributes on it, are written first, and those attributes are what make the rendering possible.

<RouteExplorer />

Change the route in that figure and watch both values move. They're the only things that differ between the fifty files.

## Which page am I?

`data-route="/about/"`.

The app is one bundle, shared by every page. `main.jsx` reads the attribute and hands it to the route table:

```js
const rootEl = document.getElementById('root');
const route  = rootEl.dataset.route || '/';
```

`routes.jsx` is an ordered list of regular expressions. `/^\/about\/$/` matches `About`. `/^\/notes\/[^/]+\/$/` matches `Note`. First match wins, which is why the patterns with a fixed second segment come before the ones that would swallow it. `/essays/tag/x/` has to be tested before `/essays/:slug/`.

That's the whole router. No history API, no link interception, no fallback route. The server already decided which page this is; the attribute just tells the client what the server decided.

The alternative would be to bake a different entry module per page, or to read `window.location`. The first means fifty bundles. The second means the page can't be rendered during the build, because there's no `window` in Node, and rendering during the build is the point.

## How deep am I?

`data-base="../"`.

`/about/` is one directory down, so everything it links to has to climb one level first. `/projects/cat/code/` is three down and climbs three. The root page climbs none, and writes `./`.

That's what makes the output portable. There is not a single root-absolute path in any of the fifty files. No `/assets/main.js`, no `/notes/`. Drop the whole directory on a domain root, in a subfolder, in a preview URL with a random path prefix, or open it off a USB stick with `file://`, and every link still points at the right thing.

I learned the value of this the tedious way. An earlier version used root-absolute paths, which worked perfectly until it was served from anywhere other than a domain root, at which point every stylesheet and script 404'd and the site rendered as unstyled text with no error to explain why.

## Written, not authored

Worth being clear that nobody types these files.

`vite.config.js` reads `src/content/`, derives the route list, and writes one HTML shell per route before the bundler starts. They're gitignored. Delete all fifty and the next build recreates them.

That's why the attributes can be trusted: they're computed from the same route list that produced the filename. The file at `notes/your-first-note/index.html` carries `data-route="/notes/your-first-note/"` because both came out of the same loop.

I did manage to forget this about my own build. When I was packaging the project to upload, I included the fifty generated files along with the source, on the theory that it removed a variable. It added one. The shell's script tag is extensionless on purpose, which is only a valid URL after the bundler rewrites it, so the stale copies I'd shipped sat in the output asking the browser for a file called `main` with no extension:

```
GET /src/app/main  404 (Not Found)
```

The upload is source only now. The sole HTML in the project is HTML the build wrote, which is the invariant this whole section rests on and which I'd quietly broken by hand.

## The guard that earned its keep

Generating directories at the root of your own repository is the kind of code that eats a project. So the generator keeps a list of names it will never create or delete (`src`, `dist`, `docs`, `node_modules`, `.git`) and throws if a content slug would collide with one.

It caught something real on its first run. The output directory was called `build/`. The build-series posts you are reading route at `/build/<slug>/`.

Generation would have written entries into the output directory, and then deleted them on the next run while cleaning up after itself. The guard turned a confusing intermittent failure into an error message with a slug name in it.

The output directory is called `dist/` now.
