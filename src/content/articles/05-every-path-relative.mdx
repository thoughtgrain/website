## The function

`relativeHref(from, to)`. Both arguments are root-relative paths; the return value is what actually goes in the HTML.

```js
relativeHref('/projects/cat/code/', '/notes/')   // '../../../notes/'
relativeHref('/products/',          '/feed.xml') // 'feed.xml'
relativeHref('/notes/',             '/notes/')   // './'
```

The second one is the interesting case.

## Dropping what's shared

The naive version is "prefix with the page's depth". From `/products/`, that turns `/products/feed.xml` into `../products/feed.xml`. Correct, in that it resolves to the right file, and silly, because it climbs out of a directory only to walk straight back into it.

So before climbing, the function counts how many leading segments the two paths already have in common, and drops them:

```js
let shared = 0;
while (shared < fromSegs.length && shared < toSegs.length
       && fromSegs[shared] === toSegs[shared]) shared += 1;

const rest = toSegs.slice(shared);
const up   = '../'.repeat(fromSegs.length - shared);
```

This also fixed two links the old generator had been getting wrong for months. The tag chips on `/essays/tag/tag-one/` pointed at `/essays/tag/tag/`, and the project tiles under `/projects/cat/code/` pointed at `/projects/cat/projects/`. Both were invisible, because JavaScript intercepted the clicks before the browser ever tried to follow them. With JS off, they 404'd.

The old build had fourteen broken internal links out of 908. This one has none out of 993, and I only know that because I started crawling the output.

## The same error, per page

Relative paths matter in the HTML. They turn out to matter in the module graph too, for a different reason.

I had the entry shells referencing the app like this:

```html
<script type="module" src="/src/app/main.jsx"></script>
```

Root-absolute, which Vite resolves against its own root. That works under a plain `vite build`. It does not work under CodePen's, which doesn't map `/` to the Vite root, and the result was one of these per entry:

```
Failed to resolve /app/main.jsx from /about/index.html
Failed to resolve /app/main.jsx from /bookshelf/craft-book/index.html
Failed to resolve /app/main.jsx from /bookshelf/essays-book/index.html
…
```

One per entry. The same message, over and over.

The fix was the depth prefix the page already had. What makes this worth writing down is that the *first* version of this code was relative, and I'd moved it to absolute to fix a bug that was actually a missing `../`, not a problem with relativeness. I removed the right mechanism because I'd implemented it wrong.

## The extension test

Then a second, subtler version of the same problem. The build I was targeting compiles `.jsx` to `.js` before the bundler runs, and doesn't rewrite the specifiers inside. So:

```
Could not resolve './App.jsx' in src/app/main.js
```

Note the filename. `main.js`. By that point `App.jsx` is `App.js`, and the specifier points at a name that no longer exists.

The obvious fix is to write `./App.js`. I tested it before committing to it:

| specifier | result |
| --- | --- |
| `./app/main.jsx` | builds |
| `./app/main.js` | **fails** |
| `./app/main` | builds |

`.js` fails because Vite maps a `.js` specifier to `.ts` and `.tsx`, never `.jsx`. So writing the extension that works *there* breaks it *here*.

Extensionless works in both: `resolve.extensions` finds `.jsx` locally and `.js` wherever the JSX has already been compiled out. Forty-two import statements across sixteen files lost their extensions.

## The rule that fell out

There is now a plugin in the build that refuses to compile if any import names a `.jsx` file:

```
Error: explicit .jsx import specifier in:
  src/app/main.jsx:24
Drop the extension, which resolves to .jsx locally and .js wherever
the JSX has already been compiled out.
```

I added it because this class of bug is invisible locally and fatal on CodePen, and I'd already spent several rounds rediscovering it. A build that can only fail somewhere you can't see is worth teaching to fail where you can.
