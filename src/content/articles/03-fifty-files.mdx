<Dropcap text="Open the network tab on any page of this site and you will see one HTML document, one stylesheet, one script. The document already contains every word on the page. Nothing has to run before you can read it." />

That sounds unremarkable. It took me three rewrites to get there.

## What actually arrives

Ask for `/about/` and the server hands you a file that lives at `about/index.html`. Ask for `/projects/cat/code/` and you get `projects/cat/code/index.html`. There are fifty of these. The filesystem is the router.

No rewrite rules. No `try_files`. No catch-all that serves one page and lets JavaScript sort out which one you meant. Each URL is a path, each path is a directory, each directory has an `index.html` in it with the words already inside.

<BuildStepper />

React is still here — it renders those fifty files during the build, and it hydrates them in the browser so the drawer and the tag filter work. But if the script fails to load, you still get the site. You get a slightly less interactive version of exactly the thing you asked for.

## Where it has to run

One constraint shaped most of what follows: I wanted this to build and run on **CodePen**.

Not as a demo — as somewhere the actual site lives, editable in a browser, no local checkout required. CodePen 2.0 runs Vite under the hood, so a standard Vite project is in principle exactly what it wants.

In practice "in principle" did a lot of work in that sentence, and the next four posts are largely the gap between the two. But it's worth saying up front that almost every decision here — relative paths everywhere, no bundler in `package.json`, extensionless imports, a build that degrades instead of failing — comes from that one requirement. A site that only builds on my machine isn't finished.

It also pushed the architecture in a direction I'd have wanted anyway. Output that works from any path, with the words already in the HTML, is portable by construction. CodePen was the forcing function; it isn't the only beneficiary.

## The detour I took

Partway through, I converted the whole thing to a single-page app. One `index.html`, react-router reading the address bar, every page drawn in the browser.

It was a reasonable-sounding suggestion and I followed it further than I should have. Here is what the build produced:

```
dist/
  index.html          ← one file
  assets/index.js
  assets/index.css
  feed.xml …
```

One HTML file. Fifty routes.

## What that cost

Three things, and I only really felt the first one when I tried to host it somewhere ordinary.

**The host has to be in on it.** Every URL except `/` resolves through the router, and the router only runs after the page has loaded. So the host must rewrite unknown paths to `index.html`. GitHub Pages doesn't. Without that rewrite, `/notes/your-first-note/` is a 404 before any JavaScript has had a chance to exist.

**Everything else gets an empty div.** The HTML that arrives is `<div id="app"></div>`. That is what a crawler indexes, what a link preview quotes, and what someone with JavaScript disabled reads. The words only exist after React runs.

**Every link has to be absolute.** A router matches on pathname, so a relative href would resolve against whatever page you happened to be standing on. Which means the output can only be served from a domain root — not a subdirectory, not `file://`.

None of those are bugs. They're the deal you make. I just didn't want to make it for a site whose entire job is to hold words that should still be there in ten years.

## The shape it settled into

So: fifty files, each one a real document, each one prerendered.
