## What are we even drawing?

Let's start with what a machine is. On the OP-XY, a machine is a synth, an effect, or something that plays notes into another track. When you select one, the screen belongs to it. Teenage Engineering take that seriously: the drum page draws the drum, the filter page draws the curve you are bending. You turn a knob, a thing on the screen moves, and it moves by about as much as the sound changed.

Now picture a machine someone ported over from a Eurorack module. Four parameters, four numbers in the header, and under them, nothing. It works. It just looks like a spreadsheet cell in a room full of instruments.

So the brief for every screen I design is one sentence long. Find the one object the sound acts on, draw it in the device's greys, and make every knob move something you can see, in proportion to what you hear.

<ScreenCells machine="kiln" cells="rest,playing" caption="Meet Kiln, a struck ceramic bowl. Glaze damps it, cracks make it ring out of tune. On the left it is at rest; on the right a note is playing. Everything you see is one of eight greys on black." />

Here's the thing. One screen is a design job. Thirty screens, with an agent drawing most of the candidates, is a process problem. The first few rounds taught me that an agent will cheerfully draw you an orrery for a reverb, five times in a row, with total confidence. A style guide was not going to be enough. I needed rules that could say no.

## Eight greys and a ruler

Before any of the fun parts, the numbers, because the device does not negotiate.

<GreyRamp caption="The OP-XY's grey ramp, with each grey's contrast against the black screen. Text needs 4.5:1, so the darkest grey I let words wear is #7d7d7d. Parts that carry meaning need 3:1. Everything darker is ground: meshes, fills, the floor a drawing stands on." />

Then the rest of it. Text no smaller than 8 pixels, in a font I cannot legally install on my laptop. A drawing is made of bound shapes with at most 64 points each, and only a handful of them may change outline. The device can redraw about twenty nodes a frame before it starts to stutter. And the one that shapes everything else: nothing moves at rest. An idle machine is a still picture.

I wrote all of that down first, before any tool existed, and I gave every number a link to the line in open-xy's documentation it came from, pinned to a commit. That sounds fussy. It is also the reason I can tell, months later, which rules are the device's and which are mine.

The same went for the process (nine phases, each with a gate I do not pass until it holds), the patterns that have worked on this screen before (a section drawing, a diagram beside a trace, a stack in depth), and the craft rules that keep a passing screen from looking like clip art: one drawing language, three line weights, one brightest thing, no text in the picture. The documents are the product. Everything below is a way of reading them, running them, or protecting them.

## Why five?

Try this experiment. Ask for three ideas and look at what comes back. Nine times out of ten you get the first idea, plus two strawmen built to make the first idea look good. I did this to myself for weeks before I noticed.

So every pass that generates design produces exactly five variants, and they have to be properly different, not five nudges of one idea. Five is enough to force a couple of directions I would never have tried. It is still few enough to lay side by side at the device's own size and judge with your eyes.

As a sentence in a document, that rule held for about a week.

## Rules a server can hold

This is where the MCP server comes in. It is the repo itself, turned into tools an agent can call, and the design pass is the part I built first because it is the part that kept slipping.

`design_pass_start` hands out five directions before anything is drawn. For a subject pass that means five angles on the machine's own idea (the mechanism, the material, a scene, a cutaway, the rule made into a physical thing) crossed with five ways of drawing. It returns five little briefs, and in Claude Code those run as five parallel designer agents, each one writing only into its own folder. Nobody sees anybody else's drawing until all five exist.

`design_pass_submit` then measures what came back. Every variant has to be a drawn frame, linted clean, with no words in the picture. A pass of written proposals is bounced. Subjects have to differ pairwise in at least two of angle, drawing language and wording, with word overlap under 0.6. Rest frames have to differ on at least 4% of the body's pixels. Anything too alike comes back marked `needs_revision`, and the only way forward is a new direction for the weakest one. Never four.

<ScreenPass machine="kiln" pass="02-subject" caption="Kiln's second subject pass. Five directions handed out first: the mechanism, the material, a scene, an exploded view, a cutaway. Five drawings back. Ten pairs checked. I picked v1, for how it would move rather than how it sat still." />

Does that feel like a lot of ceremony? It did to me too, until I read a pass record back. Every direction, every drawing, every pair's overlap score, and the state the pass ended in, all in one file next to the pictures. The process stopped being something I remembered and became something I could look at.

## Who picks?

Not the server. I want to be really clear about that, because it would have been easy to let it.

`design_pass_select` records which variant, who picked it, and why, and it refuses a call without a reason. `design_pass_reject` records that the person looked at all five and wanted none of them, and closes the pass so a new one can start with that reason as its brief. A reviewer can rank the five in the notes, and the notes say in so many words that a ranking is not a pick.

Kiln's first subject pass is my favourite example, because I turned it down. Five real directions: a field of glaze tiles, a section with a star chart over it, a modal schematic, an oscilloscope, an orrery of the bowl's own modes. I can tell you exactly what I said, because it is in the file: none of the five land, five new unique directions. The next pass started from that line, and it is the one above.

## Seen as much as heard

My favourite rule in open-xy's own guidance is that a control should be seen as much as it is heard. A quiet control with a huge visual swing is lying to you. A loud one with a tiny mark leaves you guessing.

So each control gets one visual channel (rotation, position, uniform scale, shape, shade, count), and how far it travels scales with how much it changes the sound, which I score from one to five at intake. The floors are numbers, not vibes: 24 pixels of position, 30 degrees of rotation, 1.6 times of scale, 12 items of count, 16 pixels of shape change. A change in shade never clears a floor on its own, because a small grey step is the easiest thing on this screen to miss.

The server has a tool for this. It renders each control's 0, 50 and 100 frames and measures how much of the screen actually changed. A control under its floor goes back a phase and gets more travel. The score is never lowered to make the test pass.

## What the server is, mechanically

Plain Python, standard library only, nothing to install. One setup command registers it with Claude Code, Claude Desktop, Codex, LM Studio or Ollama, merging into whatever config is already there. Its tools come in four groups.

**Knowledge.** The guidelines by document and section, a search across them, the categories, the patterns filtered by category, the device numbers, the library of audited screens. The agent reads the protocol the same way I do, and quotes it back when it stops to ask me something.

**Checks.** The scripts I had been running by hand, wrapped: lint a definition against the SDK's contract, lint frames against the device's drawing rules, measure perceptibility, tile a contact sheet. Plus one new one that renders a frame to a PNG and hands it back as an image, so a vision model looks at the drawing instead of reasoning about SVG text.

**Design passes.** The little state machine above.

**Training.** When a screen teaches the guidelines something (a pattern that worked, a pitfall that cost a week), the lesson goes back into the documents through a pipeline rather than an edit. One agent drafts the proposal, a second audits it against the constraints, a third reviews it for whether it stays true to the device's look, then a deterministic gate checks the mechanics, and then a person approves it from a terminal. Nothing touches the real documents before that. The gate also refuses any proposal that tries to change the number five.

There is a compact profile of sixteen tools with short descriptions, so the whole thing fits in a small local model's context. Grey is the default, and colour is an override a person sets once in a config file, so no agent can switch it on by asking nicely. Red is refused either way, because the device uses it for recording.

## What's next

Everything only a device can prove is still marked pending: how the real font measures, how the rasterizer treats the thinnest lines, whether the motion feels right in the hand. The next step is photographs from an OP-XY beside each contact sheet, and the first entries into the library of screens that have passed audit.

The repo is built to hold more modules beside this one (sequencing workflows, preset design, sound-design notes) without disturbing it. For now it is one module, one protocol, one server, and a growing stack of five-at-a-time decisions with a person's name on each.
