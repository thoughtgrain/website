## Premise

A machine on the OP-XY is a synth, an effect, or something that plays other tracks, and when it is selected the screen is its to draw. Stock machines draw well: the drum page draws the instrument, the filter page draws the curve you are shaping. A custom machine that ships with a panel of four numbers looks like what it is, a port with the screen left over.

So the design brief was simple to say and hard to repeat: one subject the sound acts on, drawn in the device's greys, where every knob visibly moves something in proportion to what it does to the sound. Doing it once is a design job. Doing it thirty times, with an agent drawing most of the candidates, needed a process the agent could not drift away from. The [operator-design repo](https://github.com/thoughtgrain/operator-design) is that process, and the MCP server is what makes it enforceable rather than advisory.

## Write it down before you build it

The server came last. First I wrote the guidelines as plain documents, because a tool that enforces rules nobody has agreed is just friction.

- **Constraints with sources.** Every hard number (480 by 220, the eight greys, text no smaller than 8 pixels, mutable paths of at most 64 points, about twenty changed nodes per frame) links to the line in open-xy's docs it came from, pinned to a commit. When the SDK moves, I know what to re-check.
- **A protocol with gates.** Nine phases, from "does this sound earn a screen at all" to a handoff someone else can implement from. Each has an output and a condition I do not pass until it holds.
- **Patterns as descriptions, not assets.** What has worked on this screen (a section drawing, a diagram beside a trace, a stack in depth) and which kinds of machine each fits. Never traced, only borrowed from.
- **Craft and accessibility.** One drawing language per screen, three line weights, one brightest element, no text in the drawing, contrast ratios for every grey against black, and the single-cue rule: a state never rides on a shade alone.

The documents are the product. Everything the server does is a way of reading them, running them, or protecting them.

## Turning the documents into tools

The server is stdlib Python with nothing to install. It registers the repo as an MCP server for Claude Code, Claude Desktop, Codex, LM Studio and Ollama, each through one setup command that merges into the client's existing config. Its tools fall into four groups.

- **Knowledge.** The guide by document and section, a search across all of them, the categories, the patterns filtered by category, the device numbers from `tokens.json`, and the library of audited screens. The agent reads the protocol the same way I do, and quotes it back when it stops to ask.
- **Checks.** The scripts I already ran by hand, wrapped: lint a definition against the SDK's contract, lint frames against the device drawing rules, measure how much of the screen each control changes against its floor, tile a contact sheet. And one new one, render a frame to a PNG at 1:1 and hand it back as an image, so a vision model looks at the drawing instead of reasoning about SVG text.
- **Design passes.** A small state machine for the five-variant rule, below.
- **Training.** The pipeline by which a lesson from one screen becomes a change to the guidelines, further below.

The compact profile cuts that to sixteen tools with short descriptions so it fits a small local model's context. The same server, the same records.

## Making five enforceable

Every pass that generates design produces exactly five variants. Two or three candidates kept collapsing into my first idea plus two strawmen; five forces directions I would not have tried, and five is still few enough to judge side by side at 1:1. As a rule in a document it held for about a week. As a tool it holds.

`design_pass_start` assigns five directions before anything is drawn: for a subject pass, five angles on the machine's own idea (the mechanism, the material, a scene, a cutaway, the rule made physical) crossed with five ways of drawing. Patterns that fit the category are listed in each brief as inspiration, never assigned. The call returns five designer briefs, and in Claude Code those run as five parallel subagents, each writing only into its own folder.

`design_pass_submit` then measures what came back. Every variant has to be a drawn 480 by 220 rest frame, linted clean with no text in the drawing; a pass of written proposals is sent back. Subjects must differ pairwise in at least two of angle, drawing language and wording, with word overlap under 0.6. Frames must differ pairwise on at least 4% of the body's pixels at 1:1. A pass with a near-duplicate comes back as `needs_revision`, and the only way forward is a new direction for the weakest one, never four.

## The pick stays with a person

The server never chooses. `design_pass_select` records which variant, who picked it and why, and refuses a call without a reason. `design_pass_reject` records that the person wanted none of the five, and closes the pass so a new one can start with that reason as its focus. A reviewer can rank the five in the notes, and the notes say in so many words that the ranking is not the pick.

That sounds like ceremony until you read the records back. Kiln's first subject pass was five real directions, from a glaze-tile field to an orrery of the bowl's modes, and I turned them all down with one line: none of the five land, five new unique directions. The next pass started from that line. The decision, the reason and the time are in the file beside the drawings, and the [demonstration](demo/) replays them exactly as they happened.

## Checks that look at pixels

The rule I care about most comes from open-xy's own guidance: a control should be seen as much as it is heard. Each control gets one visual channel (rotation, position, uniform scale, shape, shade, count) and its travel scales with how much it changes the sound, scored one to five at intake. The floors are numbers: 24 pixels of position, 30 degrees of rotation, 1.6 times of scale, 12 items of count, 16 pixels of shape change. Shade alone never clears a floor.

The perceptibility tool renders the 0, 50 and 100 frames for each control and measures how much of the screen changed. A control under its floor goes back a phase and gets more travel; the score is never lowered to make it pass. The contact sheet puts every frame on one page so the eye can do the check the tool cannot: do the moving parts keep clear of each other at the extremes?

## Teaching it

When a screen teaches the guidelines something (a pattern that worked, a pitfall that cost a week, a category nothing fits), it goes back into the documents through training mode rather than an edit. A proposal is drafted by one agent, audited by a second against open-xy and the constraints, reviewed by a third for whether it stays true to the device's look and will help the next designer, then run through a deterministic gate: the verdicts match the current version of the changes, the three agents are different, every edit applies cleanly. Only then does it wait for a person, who approves it from a terminal.

Nothing touches the real documents before that approval. Every check runs on a temporary copy with the proposal applied. The gate also refuses any proposal that changes the number five.

## Running it anywhere

Grey is the default, and colour is an override set per client in its MCP config, so a person decides it once in a file and no agent can switch it on by asking. Red is refused either way, because the device uses it for recording. The server can point at a machine's own checkout instead of the repo, and at a local copy of open-xy so it can run the SDK's own checker on a finished machine. With a local model it can also run the auditor and reviewer itself, through any OpenAI-compatible endpoint, while approval still stays with a person.

## What it produced

The [demonstration](demo/) replays the sessions from the records the server wrote: the directions, the five drawings, the uniqueness tables, the rankings and my decisions, with their timestamps. Under the featured session is every other machine's, and under those every screen they produced, <ScreensSummary />, each at the device's own size and each linked to the step that made it.

Behind that page the files are packed rather than shipped one by one: one lossless atlas per machine, pixel-identical to the source frames, three short videos for the motion clips, and one index that says where everything sits and what was said about it. Four hundred images arrive as about fifty files and four megabytes.

## Where it is going

Everything only a device can prove is still marked pending: caption widths in the real font, how the rasterizer treats the thinnest lines, whether the motion feels right in the hand. The next step is photographs from an OP-XY beside each contact sheet, and the first entries into the library of screens that passed audit.

The repo is built to hold more modules beside this one (sequencing workflows, preset design, sound-design notes) without disturbing it. For now it is one module, one protocol, one server, and a growing stack of five-at-a-time decisions with a person's name on each.
